# 新项目创建与模板升级

## 已确认

- 首版复制模板源码目录或获取源码包，再用容器内初始化命令设置项目名称、品牌及配置，不另做直接生成新目录的脚手架生成器。
- 初始化提供人工交互菜单及 Agent 一行参数方式，不要求宿主安装 npm、Node.js 或 Java；具体参数及文件覆盖规则待细化。
- 稳定共通能力通过版本化共享包分发，项目保有业务代码、项目配置和应用骨架。
- 首版共享包以带版本及校验信息的包文件随模板发布，新项目引用包文件；升级提案替换包文件和版本记录，不要求独立私有包仓库。包获取与构建均在容器内。
- 共享包采用统一发布版本与清单，以受检查组合发布，新项目锁定明确版本，不自动跟随 latest。前后端仍独立构建发布，须校验组合兼容性；应用业务版本不必与模板版本相同。
- 新项目通用改进经审查后反哺模板，业务专属内容与数据留在项目。
- 各项目在自己的受控自动化中默认每天检查一次模板版本清单，频率可覆盖；发现更新后在容器内生成升级提案及检查结果。同时提供手动 CLI 检查入口，模板无需持有全部项目写权限，不在应用业务进程中增加定时检查服务。
- 升级提案默认交付可审查补丁、版本变化清单及检查报告，供维护者应用或纳入自己的仓库流程；首版不要求远程 PR 集成。由项目维护者确认应用，不自动合并或部署。
- 升级提案处理共享依赖及必要骨架迁移：在临时工作区比较原模板基线、项目现状与目标模板，准备三方合并候选，无冲突部分生成补丁。
- 有冲突或缺基线时列明人工处理项，未解决前不标记可直接应用，不改写现用源码，不默认迁移业务文件；无文本冲突仍须通过语义及行为检查。
- 支持从当前版本到明确支持目标的累计升级提案，包含全部必要中间迁移及检查，不要求逐版部署；路径元数据缺失或不支持时阻断并说明分步路径，不跳过必要数据库迁移。

- 首版公共修复集中发布于最新稳定版本，旧项目通过升级提案接收；不承诺旧主版本补丁回补，不要求立即部署，升级仍受支持路径约束。

## 分发事实核对

通过 Context7 核对 npm 官方文档：支持按包名及版本从兼容 registry 获取依赖，也支持本地或 URL tarball。两类方案均可在容器构建中执行，不因此要求宿主安装 npm。已选择版本化包文件载体，具体发布与受控获取设施尚待确定。

依据：[registry](https://github.com/npm/cli/blob/latest/docs/lib/content/using-npm/registry.md)、[npm install](https://github.com/npm/cli/blob/latest/docs/lib/content/commands/npm-install.md)。
