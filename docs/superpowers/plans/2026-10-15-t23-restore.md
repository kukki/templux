# T23 Explicit Database Restore Implementation Plan

> Native execution by the assigned teammate; TL approved the design in Team mailbox. No delegation or production deployment operations.

**Goal:** Restore a trusted custom archive to an explicitly named existing database, keeping access closed until verified data and session revocation commit together.

**Architecture:** A dedicated restore service owns preflight, durable connection fencing and a single psql transaction. Original mode composes the existing maintenance halt; independent mode proves database identity differs. The CLI coordinates confirmation and reports stage/run ID without credentials. No migration or automatic deployment/connection switch.

**Tech Stack:** Node24, pg, container PostgreSQL18.6 pg_restore/psql, existing Docker Compose management.

**Spec:** Gitea Swython/Templux #24/#1; docs/specs/backup-and-recovery.md; maintenance-operations.md.

## Constraints

- Original deployment0004, .env, presentation, human identities and Feishu remain untouched.
- Required mode/target/archive/expected SHA256/confirm/overwrite; target is `current` or explicit `env:VARIABLE`, never a credential URI in argv.
- Preexisting target; ownership/identity/termination permissions required, CREATEDB not required. Only exact current migration history supported. Archive must be trusted full custom format using COPY migration data.
- pg_restore clean replaces archive objects; extra target objects remain. Confirmation states this is not whole-database erasure.
- Source bytes copied to private staging and SHA verified before any halt. Tools fully decode; migration COPY history validated before destructive work.
- Identity uses system_identifier + database OID, rejects inability to prove. Preconnect to distinct management database (`postgres`, or explicit env target management URL), same cluster verified, so failure rescue remains possible.
- Original: acquire maintenance operation lock, halt with T21 barrier and stop business, create persistent external block, then connection fence and restore. Ordinary resume cannot clear block.
- Keep only management and already-connected psql target sessions; close new connections before terminating others. Connection fence remains on all post-fence failures.
- One psql transaction restores, validates history/structure, deletes all sessions/OAuth/link requests, sets SQL offline, increments gate/version, inserts strong audit with run ID and hashes. No old login proof survives.
- Confirm COMMIT, then verify through retained target management client before allowing connections. No automatic resume; failed/unconfirmed commit or reopen leaves closed diagnostic state. Host rescue from management DB documented and exercised.

## Review Focus

1. Same database via different host/URI spelling: compare server and database identities before halt.
2. Replay of online/gate0 and matching old receipt: external block + datallowconn fence, final SQL offline.
3. Audit/validation failure and commit ACK loss: no success; fence retained, no retry.
4. Untrusted paths/symlinks/ownership, tampered bytes or unsupported archive version: fail before service changes.
5. No-CREATEDB owner and unavailable management/identity permissions: preflight fails without disruption; authorized owner recovery exercised.
